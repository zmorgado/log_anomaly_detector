# Log Anomaly Detector

A hybrid two-stage system for detecting and classifying network security threats, built as the final project of the *Curso Intensivo en Inteligencia Artificial* (CEI Seville).

It combines an **unsupervised LSTM Autoencoder** that flags anomalous network flows with no prior knowledge of the attack, and a **supervised multiclass XGBoost** classifier that identifies the specific threat type for the flows marked as anomalous.

## Motivation

Security Operations Center (SOC) teams are flooded with security alerts, which forces highly skilled staff to spend time triaging incidents that often turn out to be irrelevant. The goal of this project is to show how machine learning can complement current cybersecurity practices by automatically detecting anomalies in network traffic and classifying the associated threat — reducing the "human in the loop" workload for known attacks so analysts can focus on genuinely unknown ones.

## Architecture

The pipeline runs in two stages:

```
Network flow (36 features)
        │
   StandardScaler + sliding window (20 × 36)
        │
   LSTM Autoencoder  (encoder → latent 32 → decoder)
        │
   Reconstruction error > anomaly threshold?
        │
   ┌────┴─────────┐
  No              Yes
   │               │
 BENIGN     XGBoost (multiclass, balanced)
                   │
        DoS Hulk / Slowhttptest / slowloris
```

1. **LSTM Autoencoder (detection).** Trained exclusively on benign traffic, it learns to reconstruct normal network-flow sequences. Sequences it cannot reconstruct well — i.e. with a reconstruction error above a calibrated threshold — are flagged as anomalous. Being unsupervised, it can flag attacks of any kind, including unknown ones.
2. **XGBoost (classification).** A supervised multiclass classifier (`multi:softprob`) that operates on the flows marked as anomalous and assigns the specific attack type.

## Dataset

[CIC-IDS2017](https://www.unb.ca/cic/datasets/ids-2017.html) (MachineLearningCVE) — Canadian Institute for Cybersecurity, University of New Brunswick. Features generated by CICFlowMeter over real traffic captures.

- `dataset/Monday-WorkingHours.pcap_ISCX.csv` — benign traffic, used to train the LSTM Autoencoder.
- `dataset/Wednesday-workingHours.pcap_ISCX.csv` — mixed traffic with DoS Hulk, Slowhttptest and slowloris attacks, used to train and evaluate XGBoost.

> The CSV files are stored with [Git LFS](https://git-lfs.github.com/). Install it (`git lfs install`) before cloning to retrieve the actual data.

## Methodology

**Preprocessing**
- Cleaned NaN and ±inf values (a known CICFlowMeter extraction artifact).
- Reduced each dataset to 50,000 rows, preserving order (required by the LSTM).
- Feature selection via a correlation matrix (0.90 threshold) plus domain documentation, ending with 36 relevant features.
- `StandardScaler` fitted only on benign traffic to avoid data leakage.
- `LabelEncoder` for the attack labels.
- Sliding windows of 20 consecutive flows (stride 1) to build the 3D tensor the LSTM requires.

**Training**
- LSTM Autoencoder: unsupervised on benign Monday traffic, MAE loss, Adam optimizer, batch size 256, early stopping. ~55k trainable parameters, converged in ~48 epochs.
- Anomaly threshold set at the 95th percentile of the benign validation reconstruction error (final value: 0.4426).
- XGBoost: supervised on 70% of Wednesday traffic, stratified split, balanced sample weights, 30 estimators, max depth 6, learning rate 0.1.

## Results

**XGBoost in isolation** (test set, stratified): F1-score ≈ 1.00 across all four classes — confirming the selected features are sufficient when labels are available.

**Full pipeline (LSTM + XGBoost):**

| Class            | Precision | Recall | F1   | Support |
|------------------|-----------|--------|------|---------|
| BENIGN           | 0.72      | 1.00   | 0.84 | 25,466  |
| DoS Hulk         | 1.00      | 0.42   | 0.59 | 14,887  |
| DoS Slowhttptest | 1.00      | 0.90   | 0.95 | 5,499   |
| DoS slowloris    | 0.99      | 0.86   | 0.92 | 4,129   |
| **Accuracy**     |           |        | 0.80 | 49,981  |

- **Perfect recall on BENIGN (1.00):** legitimate traffic is never misclassified as an attack — no false alarms.
- **Near-perfect precision on attack types:** when the system names a threat, it is almost always right.
- **Low recall on DoS Hulk (0.42):** a limitation inherited from the detection stage — DoS Hulk generates seemingly valid HTTP requests whose features overlap with benign traffic, so its reconstruction error stays below the anomaly threshold and ~9,750 flows never reach XGBoost.

## Limitations & future work

- Attacks that do not noticeably perturb flow features escape the unsupervised detector. This was measured directly: on unseen traffic, **DoS GoldenEye is detected in 11.2% of windows — statistically indistinguishable from the 11.1% false-positive rate on benign traffic in the same region** (median reconstruction error 0.2785 vs 0.2682 for benign). Like DoS Hulk, GoldenEye issues syntactically valid HTTP requests, so the flows it produces sit inside the distribution the autoencoder learned as normal. The detector is not partially seeing these attacks; it is not seeing them at all.
- Not every unknown attack is invisible, though. Heartbleed — an attack class entirely absent from training — is detected in 62.5% of its windows (median error 0.4582, above the 0.4444 threshold), and XGBoost then labels it `BENIGN` because it has no class for it. Detection and classification fail independently, which is the argument for keeping the two stages separate.
- Mitigations worth testing for the flow-feature blind spot (DoS Hulk). Possible improvements: additional features that better characterize these flows, larger sliding windows (20 → 100), or combining the LSTM with another unsupervised detector such as Isolation Forest.
- The dataset was reduced for runtime; scaling to the remaining CIC-IDS2017 attack classes (PortScan, Brute Force, Web Attacks, Infiltration, Botnet) would test how the architecture generalizes.
- Adding an LLM-generated explanation step that takes the highest-error features, the predicted class and flow context to produce a human-readable report for analysts.

## Local setup

Requires Python 3.12 — TensorFlow does not support Python 3.13+.

```bash
python3.12 -m venv .venv
source .venv/bin/activate    # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

The CSV files are stored with Git LFS; run `git lfs pull` after cloning to fetch them.

## Environment

Local development uses Python 3.12 (TensorFlow does not support 3.13+). Main libraries: TensorFlow 2.16.1 (Keras 3.15.1), XGBoost 2.0.3, scikit-learn 1.3.2, pandas 2.1.4, numpy 1.26.4, matplotlib 3.8.4, seaborn 0.13.2. Exact pins are in `requirements.txt`.

The original models were trained on Google Colab (GPU T4); the pinned local environment reproduces them (anomaly threshold 0.4444 vs 0.4426 on Colab).

## Reproducible training

After completing the local setup above, run the full pipeline from the repository root:

```bash
python scripts/train.py
```

The script reads the two CSVs from `dataset/` and writes the fitted scaler,
label encoder, XGBoost model, LSTM autoencoder, calibrated threshold, training
history, and evaluation metrics to `artifacts/`. Use `--data-dir` or
`--artifacts-dir` to select different input/output locations.

## Interactive demo

**[log-anomaly-detector-gold.vercel.app](https://log-anomaly-detector-gold.vercel.app/)**

A static page in `web/` replays the trained pipeline over an **unseen slice** of Wednesday
traffic (absolute rows 67,250–69,269 — outside the 40k–90k range used to fit XGBoost, and
the scaler was fitted on Monday benign traffic only). To run it locally instead:

```bash
open web/index.html          # macOS; or just open the file in a browser
```

No backend and no build step. All inference is precomputed by `scripts/export_demo.py`
into `web/demo_feed.json` (345 KB), so the page only replays results:

```bash
python scripts/export_demo.py
```

The feed stores the **raw reconstruction error per window**, never a benign/anomalous
verdict. The page recomputes `error > threshold` in the browser, which is what makes the
threshold draggable: moving it re-derives every verdict, the incident queue, and the live
precision/recall figures. XGBoost predictions are exported for every window, so lowering
the threshold immediately classifies windows the calibrated run never flagged.

Dragging the threshold traces the precision/recall tradeoff on this slice:

| Threshold | Precision | Recall | Alerts |
|-----------|-----------|--------|--------|
| 0.15      | 0.44      | 0.99   | 1,985  |
| 0.35      | 0.68      | 0.88   | 1,143  |
| **0.4444** (calibrated) | **0.83** | **0.86** | **907** |
| 0.60      | 0.98      | 0.74   | 663    |
| 1.00      | 0.99      | 0.19   | 167    |

F1 peaks slightly *above* the shipped threshold on this slice, so the 95th-percentile
calibration is defensible rather than optimal — the demo lets you find that yourself.

Note that this slice contains no DoS Hulk, so the pipeline's main weakness (0.424 recall)
is reported in the demo's metrics panel rather than visible in the stream. `design.md`
documents the visual specification the page implements.
